# Core delivery role handoffs

Use this reference whenever a core Workbench delivery role—designer, reviewer,
or implementer—is delegated. It owns the context and authority shared by those
roles. Specialist scan and research fan-out keep their own contracts.

## Shared context

Pass this context explicitly; a fresh context must not be expected to inherit it:

- the authoritative request or Workbench outcome, including its accepted scope;
- explicit exclusions and the owned write surface, if the role may write;
- relevant foundation truth and exact repository evidence pointers;
- the selected lens and effective simplification posture;
- the current project `## Overbuilding calibration` from `.work/CONVENTIONS.md`,
  or an explicit note that it is absent and current evidence-based judgment
  applies;
- the effective execution and review postures when the assignment is a formal
  Workbench workflow; and
- the integration contract, required checks, and return evidence expected from
  the role, when relevant.

Treat the project calibration as a proportionality lens, not a checklist or a
new requirement. It applies to design and review in an adopted repository,
including loose requests, but loose use does not acquire Workbench ledger,
review-weight, convergence, packet, or closure mechanics.

## Canonical boundary instruction

Include this instruction exactly in every delegated core-delivery handoff:

> Do not invent requirements or expand scope. Work only from the user's original
> intent, the accepted item and design when present, applicable foundation truth,
> the project's overbuilding calibration, and the rational expectations of this
> project type. Treat unearned machinery as a defect. Return worthwhile ideas
> outside that boundary separately as non-blocking follow-ups.

The caller owns final synthesis and adjudication. Reviewers and designers
propose; they do not turn a preference, incident, or adjacent opportunity into a
requirement.

## Formal core-delivery roles

- **Designer — proposal-only.** May recommend a shape but does not edit the
  item, foundations, or code. Follow the return contract in
  [design](../../design/SKILL.md).
- **Reviewer — proposal-only.** Does not edit the stable target. Follow the
  packet, materiality, and adjudication contract in [review](review.md).
- **Implementer — assignment-scoped writes.** May edit only the exact owned
  surface; authority does not include scope growth or shared-catalog changes.
  Follow [execution](execution.md) and [deliver](../../deliver/SKILL.md).

## Loose delegated design or review

For a loose design or review request in an adopted repository, pass only:

1. the user's request and explicit exclusions;
2. the current project calibration, or its absence;
3. relevant repository evidence and exact pointers; and
4. the canonical boundary instruction above.

Ask for a concise proposal or findings reply. Do not pass or impose a formal
Workbench packet, item lifecycle, configured review weight, convergence rule,
or closure obligation. The main agent remains responsible for the user's
request; if the user explicitly asks to edit conventions, that is a separate
confirmed write decision.
